# LLM 분개 전체 분석 설계

> **핵심 원칙**: 규칙 기반 엔진이 전체 분개를 1차 분류하고, LLM은 중요 계정·이슈 후보·판단 불가 분개만 2차 정밀 분석하여 규칙 엔진에 넘긴다.  
> LLM은 판단 보조·후보 발굴 계층이다. 최종 세무조정 금액과 세액 계산은 규칙 엔진과 회계사 검토 흐름이 담당한다.

> ### 구현 현황 (2026-06)
> - 모델: 로컬 Ollama **gemma4** (CPU 추론 ≈ 분개 1건당 1분, 배치 5건·타임아웃 600초·num_ctx 8192·format json)
> - **LLM 단계는 선택(optional)** — 5단계 세무조정 계산은 LLM 없이 집계+규칙 엔진만으로 완료
> - 1차 분류 결과는 **한글 이슈 분류명**으로 표시 + 이슈별 분개 드릴다운·CSV
> - 2차 분석 대상은 **이슈 분류별 multiselect로 사용자가 선택** (예상 소요시간 표시)
> - **백그라운드 스레드 실행** — 다른 페이지로 이동해도 분석 계속, 진행률·자동 새로고침
> - Level 1 RAG: 이슈코드 → 조문 매핑(`legal_basis.ISSUE_TO_ARTICLE`)으로
>   law.go.kr 원문(사업연도 종료일 시행 기준)을 프롬프트에 첨부 — ChromaDB 미사용
> - 관용 파싱: 모델이 임의 이슈코드 반환 시 UNKNOWN으로 보존, None 필드 기본값 처리 (결과 유실 방지)

## 1. 배경 및 목적

규칙 기반 엔진(Rule Engine)은 계정과목 코드와 금액만으로 세무조정을 계산한다.  
그러나 실무에서는 **같은 계정과목이라도 거래 성격에 따라 세무 처리가 달라지는 경우**가 많다.

| 계정과목 | 일반 처리 | 세무조정 발생 케이스 |
|---------|---------|-----------------|
| 복리후생비 | 손금 | 대표자 가족 의료비 지급 → 손금불산입 |
| 여비교통비 | 손금 | 개인 여행 경비 → 손금불산입 |
| 이자비용 | 손금 | 건설 중인 자산에 충당된 이자 → 손금불산입 |
| 대여금 | 자산 | 특수관계인 무이자 대여 → 인정이자 익금산입 + 지급이자 손금불산입 |

분개장·계정별원장의 **적요(摘要), 거래처명, 전표 묶음, 증빙 정보**를 LLM이 분석하면  
규칙 엔진이 놓치는 세무조정 소재를 발굴하고 누락을 방지할 수 있다.

---

## 2. LLM과 규칙 엔진의 역할 분리

### LLM 역할 (판단 보조·후보 발굴)
- 분개 적요 해석 (거래 성격 추정)
- 세무조정 후보 탐지 및 이슈 코드 부여
- 관련 법령·별지 서식 후보 제안
- 특수관계인 거래 의심 탐지
- 회계사 검토 필요 사유 작성
- 계정 오류·이상 적요 탐지

### 규칙 엔진 역할 (확정 계산)
- 한도 계산 (접대비, 기부금, 감가상각, 충당금 등)
- 세액 계산 및 세액공제·감면 적용
- 최저한세 계산
- 차감납부세액 산출
- 별지 서식 금액 반영 및 최종 산출물 생성

> **LLM이 절대 하지 않는 것**: 손금불산입 금액 확정, 과세표준 계산, 세액 직접 산출

## 3. 분석 대상 데이터 (전표/거래 묶음 단위)

한 줄 분개만 보면 판단이 틀릴 수 있다. LLM에는 **전표 단위 묶음**으로 입력한다.

### 3-1. 분개 라인 필드

| 필드 | 설명 | 세무 분석 활용 |
|------|------|-------------|
| 전표번호 | 동일 전표의 분개 묶음 키 | 차·대변 상대계정, 관련 분개 연결 |
| 라인번호 | 전표 내 순서 | Audit Trail 추적 |
| 날짜 | 거래일자 | 손익 귀속 사업연도, 이자 기간 |
| 계정코드 | 더존 Smart A 코드 | 규칙 엔진 연결 키 |
| 계정과목명 | 예: 복리후생비 | 기본 분류 |
| 적요 | 거래 설명 | **핵심 — 세무 성격 판단의 주요 근거** |
| 거래처코드 | 거래 상대방 코드 | 특수관계인 매칭 |
| 거래처명 | 거래 상대방 명칭 | 특수관계인 식별, 업무 관련성 판단 |
| 차변금액 | 차변 계상액 | |
| 대변금액 | 대변 계상액 | |
| 증빙구분 | 세금계산서/카드/현금영수증/무증빙 등 | 기업업무추진비 증빙 분류에 직접 사용 |
| 증빙번호 | 카드 승인번호, 계산서 번호 등 | 중복·위조 탐지 |
| 프로젝트/부서 | 원가 귀속 | 업무 관련성 판단 보조 |
| 카드번호 일부 | 법인카드 vs. 개인카드 구분 | 개인 사용 여부 탐지 |
| 차량번호 | 업무용 승용차 관련 분개 | 차량별 비용 집계 |
| 원본 파일명 | Smart A 내보내기 파일명 | Audit Trail |
| 원본 시트명 | Excel 시트명 | Audit Trail |
| 원본 행 번호 | Excel 행 번호 | Audit Trail 및 수정 추적 |

### 3-2. 전표 묶음 예시

```
[전표 2025-000123]
라인1 | 차변: 기업업무추진비 550,000 | 적요: 거래처 골프 접대 | 거래처: 제일골프장
라인2 | 대변: 미지급금 550,000     | 적요:                  | 거래처: 제일골프장
       증빙: 법인카드, 카드번호: 1234-****-****-5678

→ LLM이 라인1+라인2를 묶어서 판단: "거래처 골프 접대, 법인카드 증빙 → 기업업무추진비 후보"
```

## 4. 2단계 분석 구조

> **핵심 원칙**: 전체 분개는 LLM 없이 규칙 기반 엔진으로 1차 분류한다. LLM은 규칙으로 판단하기 어려운 분개·중요 계정(기업업무추진비, 가지급금, 이자비용 등)·이슈 후보에 한해 2차 정밀 분석한다.

### 4-1. 처리 흐름

```
[Smart A 분개장/계정별원장 파싱]
         ↓
┌─────────────────────────────────────────┐
│  1차: 규칙 기반 분개 분류 (전체 100%)   │  ← LLM 없음
│  - 계정코드 → 세무조정 계정군 매핑     │
│  - 특수관계인 거래처 코드 매칭          │
│  - 중요 계정 지정 (기업업무추진비 등)  │
│  - 규칙 판단 불가 분개 플래그 부여     │
│  - 출력: 이슈 코드 후보 + 분류 사유    │
└────────────────┬────────────────────────┘
                 ↓
     이슈 코드 후보 / 중요 계정 / 판단불가
     → LLM 분석 대상 선별 (전체의 20~40%)
                 ↓
┌─────────────────────────────────────────┐
│  2차: LLM 정밀 분석 (선별된 분개만)     │  ← LLM 투입
│  - 기업업무추진비, 기부금, 가지급금,   │
│    이자비용, 차량, 임원보수 등          │
│  - 관련 전표 묶음 단위로 분석          │
│  - 세무조정 모듈에 전달할 구조화 JSON  │
│  - 법령 기준일 고정 후 RAG 조문 첨부   │
└────────────────┬────────────────────────┘
                 ↓
        규칙 엔진으로 전달
        (한도 계산, 세액 계산)
                 ↓
        감사추적 기록 + 회계사 검토
```

### 4-2. 세법 적용 기준일 고정

법인세는 **사업연도별 적용 법령**이 중요하다.  
단순히 최신 법령을 가져오면 안 되며, 아래 기준으로 조문을 고정한다.

| 기준 | 내용 |
|------|------|
| **기준 사업연도 종료일** | 예: 2025.12.31 |
| **신고 대상 연도** | 예: 2026년 신고 (2025 사업연도) |
| **법령 시행일** | 해당 사업연도에 유효한 조문만 사용 |
| **개정 이력 처리** | 법인세법 시행령 개정일 기준, 이전 적용분은 구법 적용 |

국가법령정보센터 API 호출 시 **시행일자 파라미터**를 사업연도 종료일로 설정하여  
해당 연도 적용 법령 조문만 조회·저장한다.

## 5. 1차: 규칙 기반 분개 분류

### 5-1. 목적

- 전체 분개를 LLM 없이 계정코드·거래처 기준으로 빠르게 분류한다
- 세무조정 관련 계정군에 이슈 코드 후보를 부여한다
- LLM 투입이 필요한 분개를 선별하여 처리 비용을 최소화한다

### 5-2. 1차 규칙 분류 로직

```python
# 계정코드 → 이슈 코드 후보 매핑 (계정코드 기반, LLM 없음)
ACCOUNT_ISSUE_MAP = {
    "판관비_기업업무추진비": "ENTERTAINMENT_EXPENSE",   # → LLM 2차 필수
    "기부금": "DONATION_CLASSIFICATION",               # → LLM 2차 필수
    "이자비용": "CONSTRUCTION_INTEREST",               # → LLM 2차 필수
    "임원급여": "OFFICER_BONUS",                       # → LLM 2차 필수
    "임원퇴직급여": "OFFICER_RETIREMENT",              # → LLM 2차 필수
    "차량유지비": "VEHICLE_EXPENSE",                   # → LLM 2차 필수
    "잡손실": "NON_BUSINESS_EXPENSE",                  # → LLM 2차 후보
    "수입배당금": "DIVIDEND_INCOME",                   # → 규칙 엔진 직행
    "벌과금과태료": "PENALTY",                         # → 규칙 엔진 직행 (전액 손금불산입)
    "외화환산손익": "FOREX_TRANSACTION",               # → 규칙 엔진 직행
}

# 특수관계인 거래처 매칭 (사전 등록 목록 기준)
if 거래처코드 in 특수관계인_목록:
    issue_code = "RELATED_PARTY_TRANSACTION"           # → LLM 2차 후보

# 규칙 판단 불가: 계정코드가 매핑에 없고 적요가 복잡한 경우
if 계정코드 not in ACCOUNT_ISSUE_MAP and 적요_복잡도 > 임계값:
    issue_code = "PENDING_LLM_REVIEW"                  # → LLM 2차 대상
```

### 5-3. 1차 규칙 분류 출력

```json
[
  {
    "journal_id": "2025-000123",
    "account_code": "판관비_기업업무추진비",
    "rule_issue_code": "ENTERTAINMENT_EXPENSE",
    "forward_reason": "중요계정_필수분석",
    "forward_to_stage2": true
  },
  {
    "journal_id": "2025-000124",
    "account_code": "임차료",
    "rule_issue_code": null,
    "forward_reason": null,
    "forward_to_stage2": false
  },
  {
    "journal_id": "2025-000125",
    "account_code": "잡비",
    "rule_issue_code": "PENDING_LLM_REVIEW",
    "forward_reason": "계정코드_미매핑_적요복잡",
    "forward_to_stage2": true
  }
]
```

> `forward_to_stage2: true` → LLM 2차 정밀 분석 대상  
> `rule_issue_code: PENALTY` 등 확정 분류 → LLM 건너뛰고 규칙 엔진 직행

## 6. 2차: 후보군 정밀 분석

### 6-1. 이슈 코드 전체 목록

| 이슈 코드 | 설명 | 연결 규칙 엔진 |
|----------|------|-------------|
| `ENTERTAINMENT_EXPENSE` | 기업업무추진비(접대비) 해당 여부·증빙 분류 | `entertainment.py` |
| `DONATION_CLASSIFICATION` | 기부금 종류 분류 (특례/일반/비지정) | `donation.py` |
| `RELATED_PARTY_LOAN` | 특수관계인 대여금 → 인정이자 | `interest.py` |
| `CONSTRUCTION_INTEREST` | 건설자금에 충당된 이자 | `interest.py` |
| `NON_BUSINESS_EXPENSE` | 업무무관비용 (손금불산입 후보) | 수동 검토 플래그 |
| `OFFICER_BONUS` | 임원 상여·성과급 한도초과 후보 | 수동 검토 플래그 |
| `OFFICER_RETIREMENT` | 임원 퇴직금 한도초과 후보 | `allowances.py` |
| `PENALTY` | 벌과금·과태료 (손금불산입 확정) | `other_adjustments.py` |
| `FOREX_TRANSACTION` | 외화 거래 → 외화환산 조정 대상 | `forex.py` |
| `DEBT_FORGIVENESS` | 채무면제익 (익금산입 후보) | `income_items.py` |
| `ASSET_GIFT` | 자산수증익 (익금산입 후보) | `income_items.py` |
| `DIVIDEND_INCOME` | 수입배당금 → 익금불산입 비율 계산 | `dividend.py` |
| `VEHICLE_EXPENSE` | 업무용승용차 관련비용 후보 | `vehicle.py` |
| `BAD_DEBT` | 대손처리 분개 → 요건 검토 | `allowances.py` |
| `INVENTORY_LOSS` | 재고 감모·평가손실 | 수동 검토 플래그 |
| `DEFERRED_REVENUE_EXPENSE` | 선급비용·미지급비용 귀속시기 오류 후보 | 수동 검토 플래그 |
| `GOVT_SUBSIDY` | 국고보조금·보험차익 수령 | `income_items.py` |
| `DEPRECIATION_MISMATCH` | 감가상각비 계상 이상 (고정자산대장 대비) | `depreciation.py` |
| `RELATED_PARTY_TRANSACTION` | 특수관계인 거래 → 부당행위계산부인 검토 | 수동 검토 플래그 |
| `UNKNOWN` | 1차 판단 불가 → 회계사 수동 검토 의뢰 | 수동 검토 플래그 |

  "affected_amount": 550000,

  "review_required": true,
  "review_reason": "거래처 골프장 이용 — 법인카드 증빙은 있으나 업무 관련성 확인 필요",
  "evidence_fields": {
    "적요": "거래처 골프 접대",
    "거래처명": "제일골프장",
    "증빙구분": "법인카드"

  "legal_basis_candidates": [
    {
      "법령": "법인세법 제25조",

    }
  ],
  "target_form_candidates": [
    "별지 제16호 기업업무추진비 조정명세서"
  ],
  "stage1_confidence": 0.90,
  "stage2_confidence": 0.87
}
```

### 6-3. 2차 정밀 분석 LLM 프롬프트 구조

```

{RAG로 검색된 법인세법 조문 — 국가법령정보센터 API 기준일 고정}

판단 원칙:
- 금액을 직접 계산하지 말 것 (규칙 엔진이 담당)
- 세무조정 후보 여부와 근거만 제시할 것
- 확신이 없으면 review_required: true로 표시할 것

[사용자 프롬프트]
법인명: (주)OOO | 사업연도: 2025.01.01~2025.12.31

특수관계인: [홍길동(대표이사), 박OO(배우자), (주)OOO물산(관계회사)]

전표 묶음:
전표번호: 2025-000123
라인1: 차변 기업업무추진비 550,000 / 적요: 거래처 골프 접대 / 거래처: 제일골프장 / 증빙: 법인카드
라인2: 대변 미지급금 550,000 / 거래처: 제일골프장 / 증빙번호: 카드승인 9876543

## 7. 규칙 엔진 연결 매핑

```
LLM 2차 분석 결과 (JSON 배열)
        ↓
tax_issue_code 기준으로 규칙 엔진 모듈에 라우팅

ENTERTAINMENT_EXPENSE    → entertainment.py    (증빙구분·금액 전달 → 한도 계산)
DONATION_CLASSIFICATION  → donation.py         (기부금 종류별 한도 계산)
RELATED_PARTY_LOAN       → interest.py         (인정이자율·기간 → 인정이자 계산)
CONSTRUCTION_INTEREST    → interest.py         (건설자금 비율 계산)
OFFICER_RETIREMENT       → allowances.py       (퇴직금 한도 계산)
FOREX_TRANSACTION        → forex.py            (외화 자료 연결)
DEBT_FORGIVENESS         → income_items.py     (익금산입 확정)
ASSET_GIFT               → income_items.py     (익금산입 확정)
DIVIDEND_INCOME          → dividend.py         (익금불산입 비율 계산)
VEHICLE_EXPENSE          → vehicle.py          (업무 사용비율 계산)
BAD_DEBT                 → allowances.py       (대손요건 충족 여부)
DEPRECIATION_MISMATCH    → depreciation.py     (고정자산 대장 대비 재계산)
PENALTY                  → other_adjustments.py (손금불산입 확정)

review_required: true    → 회계사 검토 큐 (수동 판단 대기)
UNKNOWN                  → 회계사 검토 큐 + 원본 분개 표시
```

## 8. 신뢰도 처리 방침

| 신뢰도 점수 | 처리 방법 |
|-----------|---------|
| **0.80 이상** | 규칙 엔진에 자동 전달, UI에 "AI 자동 분류" 표시 |
| **0.50 ~ 0.79** | UI에 "검토 필요" 플래그, 회계사 확인 요청, 원본 분개 함께 표시 |
| **0.50 미만 / UNKNOWN** | UI에 "불확실 — 수동 판단 요망", 원본 분개 필수 표시, 규칙 엔진 미전달 |

**핵심**: 이 시스템에서 **세무조정 소재 누락이 잘못된 분류보다 훨씬 치명적**이다.  
따라서 신뢰도 0.50 미만이라도 `issue_possible: true`인 분개는 반드시 회계사에게 표시한다.

## 9. 특수관계인 DB 관리

LLM이 거래처명으로 특수관계인을 식별하려면 사전 등록이 필요하다.

**프로젝트 기본 설정 화면에서 입력:**
- 대표이사 성명
- 임원 성명 목록 (직책 포함)
- 주요 주주 성명 및 보유 지분율
- 관계회사 법인명 (지배·종속·관계)
- 대표이사 가족 성명 (배우자, 직계존비속)

이 목록은 모든 LLM 프롬프트에 포함되어 거래처명 유사도 매칭에 사용된다.

## 10. 검증 체계

### 10-1. 테스트셋 구성

| 구분 | 목표 |
|------|------|
| 실제/가상 분개 수 | 500~1,000건 |
| 라벨링 주체 | 회계사 직접 라벨링 (이슈 코드 + 세무조정 여부) |
| 이슈 코드별 샘플 | 각 코드당 최소 30건 |

### 10-2. 측정 지표

| 지표 | 설명 | 목표 |
|------|------|------|
| **Precision** | 탐지한 후보 중 실제 세무조정 건 비율 | ≥ 80% |
| **Recall (누락률 역수)** | 실제 세무조정 건 중 탐지된 비율 | **≥ 95%** (누락 방지 최우선) |
| 신뢰도별 정확도 | High/Medium/Low 구간별 정확도 | High ≥ 90% |
| **세무조정 누락률** | 실제 세무조정 건 중 미탐지 비율 | **≤ 5%** |

> **누락률을 별도 지표로 관리**: 틀린 분류(False Positive)는 회계사가 수정할 수 있지만,  
> 세무조정 소재 누락(False Negative)은 신고 오류로 이어진다.

## 12. 보안 및 프라이버시

### 12-1. 외부 전송 금지 원칙

- **외부 LLM API (OpenAI, Claude API 등) 사용 금지**
- 모든 분석은 **로컬 Ollama 인스턴스**에서 처리
- 네트워크 연결은 법령 API (국가법령정보센터, DART)에만 허용

### 12-2. 적요 내 민감정보 처리

적요에는 임직원명, 병원명, 계좌번호, 주민번호 일부, 거래처 민감정보가 포함될 수 있다.

| 위험 유형 | 처리 방안 |
|---------|---------|
| 임직원 개인정보 | LLM 전달 전 성명 → 익명 코드 치환 옵션 |
| 계좌번호/주민번호 | 정규식으로 마스킹 후 LLM 전달 |
| 거래처 민감정보 | 프로젝트 내 로컬 저장만 허용 |
| **프롬프트 인젝션 방어** | 적요 내 특수문자 이스케이프, 시스템 프롬프트와 사용자 데이터 명확 분리 |

### 12-3. 로그 및 접근 관리

- 프롬프트·응답 로그: 프로젝트 폴더 내 암호화 저장
- 감사추적 Excel: 프로젝트 폴더 내 저장, 외부 공유 시 비밀번호 보호 권장
- 법인별 데이터 격리: 프로젝트 파일(.taxproj)은 법인/사업연도별 독립 폴더에 저장

## 14. 플랜 반영 (기존 대비 변경)

| 항목 | 기존 | 변경 |
|------|------|------|
| LLM 역할 | "일부 계정 분류 보조" | **후보군·중요계정·판단불가 분개만 2차 정밀 분석** |
| 처리 구조 | Pre-filter → LLM | **규칙 기반 1차(전체) → LLM 2차(선별) → 규칙 엔진** |
| 1차 처리 | LLM 경량 스캔 (전체) | **계정코드 매핑 테이블 + 특수관계인 매칭 (LLM 없음)** |
| LLM 출력 | 설명형 텍스트 | **구조화 JSON (이슈코드·신뢰도·법령·서식 포함)** |
| 세법 기준 | 최신 법령 | **사업연도 종료일 고정 조회** |
| 검증 | 없음 | **누락률 우선 측정 테스트셋 구성** |
| 감사추적 | 항목별 결과만 | **원본 행번호·프롬프트버전·모델명·법령기준일 포함** |
| 보안 | 로컬 LLM 언급 | **프롬프트 인젝션 방어·개인정보 마스킹·암호화 로그** |
