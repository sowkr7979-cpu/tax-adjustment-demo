# LLM 검토보조·자료요청·메모생성 설계

> 기존 명칭은 "LLM 분개 전체 분석"이었지만, 실무 적용 기준으로는 방향을 바꾼다.  
> 로컬 LLM은 느리므로 분개를 대량 정밀분석하지 않는다.  
> **규칙엔진과 체크리스트가 만든 검토 큐를 사람이 검토하기 좋게 요약하고, 자료요청·검토메모 초안을 작성하는 보조 계층**으로 사용한다.

---

## 1. 결론

세무조정 용역에서 LLM의 핵심 역할은 "모든 분개를 읽고 판단하는 것"이 아니다.

실무상 병목은 다음에 있다.

- 어떤 자료를 더 받아야 하는지
- 어떤 거래가 검토대상인지
- 어떤 조정 항목이 누락될 수 있는지
- 고객에게 어떤 문구로 자료를 요청할지
- 조서에 어떤 검토메모를 남길지
- 회계사가 최종 판단해야 할 쟁점이 무엇인지

따라서 LLM은 다음 용도로 제한한다.

```text
규칙 기반 분류/집계/체크리스트
  -> 고위험·예외·판단필요 거래 큐 생성
  -> 회계사가 검토할 항목 선택
  -> LLM이 요약, 자료요청 문구, 검토메모 초안 작성
  -> 회계사가 확정
```

LLM 결과는 세무조정 금액, 과세표준, 세액, 소득처분을 직접 확정하지 않는다.

---

## 2. 사용하지 않는 방향

아래 방식은 실무 적용성이 낮으므로 기본 전략에서 제외한다.

```text
전체 분개
  -> LLM 정밀분석
  -> LLM 결과를 규칙엔진에 전달
  -> 세무조정 계산
```

제외 사유:

- 로컬 Ollama CPU 추론 기준 1건당 수십 초에서 1분 이상 소요될 수 있다.
- 10,000건 중 20%만 분석해도 수십 시간이 걸릴 수 있다.
- LLM이 세무판단을 안정적으로 확정하지 못한다.
- 대량 분석 결과를 사람이 다시 검토해야 하므로 시간 절감 효과가 낮다.
- 규칙엔진이 이미 잘 처리하는 항목까지 LLM에 보내는 것은 중복이다.

---

## 3. 새로운 역할 분리

### 3-1. 규칙엔진이 담당하는 것

- 전체 분개 100% 스캔
- 계정코드·계정명·적요·거래처 기반 이슈 후보 분류
- 세무조정 산식 계산
- 접대비, 기부금, 감가상각, 지급이자, 인정이자, 승용차, 충당금 등 계산
- 전수 검토 체크리스트 생성
- 자료요청 후보 생성
- 법령 매핑과 별지15호 요약 행 생성

### 3-2. LLM이 담당하는 것

- 검토 큐 요약
- 고객 자료요청 문구 작성
- 항목별 검토메모 초안 작성
- 유사 거래 패턴 묶음 설명
- 회계사가 선택한 소수 거래의 쟁점 정리
- 법령 원문을 바탕으로 한 검토 포인트 문장화

### 3-3. LLM이 하지 않는 것

- 손금불산입 금액 확정
- 익금산입 금액 확정
- 과세표준 계산
- 산출세액·최저한세·차감납부세액 계산
- 소득처분 확정
- 법령에 없는 임의 규칙 생성
- 회계사의 최종 판단 대체

## 4. 업무 흐름

### 4-1. 전체 흐름

```text
[2단계 자료 업로드]
  재무제표·분개장·고정자산대장·계정별명세서 파싱

[3단계 수기 입력]
  전기 유보, 이월결손금, 특수관계인, 차량, 기부금, 이자비용 등 판단자료 입력

[4단계 AI 검토 보조]
  규칙 기반 검토 큐 확인
  고위험 항목·자료요청·검토메모 생성
  회계사가 필요한 항목만 선택해 LLM 보조 실행

[5단계 계산·검토]
  규칙엔진 계산
  검토메모·자료수취 상태 반영
  회계사가 최종 판단

[6단계 출력]
  검토패키지 PDF
  감사추적 Excel
  .taxproj
  추천 별지서식
```

### 4-2. LLM 실행 단위

LLM은 분개 한 줄 단위로 대량 실행하지 않는다.

대신 다음 단위로 실행한다.

| 실행 단위 | 예시 | 목적 |
|---|---|---|
| 이슈 그룹 | 접대비 의심 120건 | 전체 패턴 요약 |
| 거래처 그룹 | 특정 골프장·병원·리조트 거래 | 업무관련성 검토 포인트 |
| 계정 그룹 | 복리후생비, 여비교통비, 지급수수료 | 비정상 적요 요약 |
| 전표 묶음 | 회계사가 선택한 10건 | 정밀 검토메모 |
| 자료요청 묶음 | 차량·기부금·이자비용 자료 부족 | 고객 발송 문구 |

## 5. 검토 큐 생성 기준

LLM 이전 단계에서 규칙엔진이 검토 큐를 만든다.

### 5-1. 자동 검토 큐

다음 항목은 LLM 없이도 검토 큐에 올라간다.

| 항목 | 큐 생성 기준 | LLM 용도 |
|---|---|---|
| 접대비·기업업무추진비 | 골프, 유흥, 선물, 백화점, 고액 식대 | 거래 패턴 요약, 자료요청 문구 |
| 복리후생비 | 병원, 가족, 개인, 학원, 여행 키워드 | 업무관련성 검토메모 |
| 여비교통비 | 휴양지, 가족, 주말, 해외 키워드 | 출장 증빙 요청 문구 |
| 지급이자 | 건설, 공사, 자산취득, 차입금 키워드 | 건설자금이자 검토 포인트 |
| 가지급금·대여금 | 특수관계인·임직원·대표자 거래 | 인정이자/업무무관이자 검토 포인트 |
| 기부금 | 학교, 종교, 협회, 후원, 찬조 | 분류 검토 요청 문구 |
| 차량비 | 차량번호, 렌트, 리스, 보험, 주유 | 운행기록부·보험 자료요청 |
| 벌과금·과태료 | 가산세, 과태료, 벌금, 범칙금 | 조서 메모 초안 |
| 부당행위 | 특수관계인 매출·매입·자산거래 | 시가자료 요청 문구 |

### 5-2. 고위험 우선순위

LLM 실행 대상은 위험도와 금액 기준으로 제한한다.

```text
1순위: High 위험 + 금액 중요
2순위: 법령상 판단자료가 없으면 계산 불가
3순위: 고객에게 자료요청 문구가 필요한 항목
4순위: 회계사가 직접 선택한 거래
```

기본 목표:

```text
전체 분개의 0.5% ~ 3%
또는 이슈별 상위 20~100건
또는 회계사가 선택한 거래만
```

## 6. LLM 기능 설계

### 6-1. 검토 큐 요약

입력:

- 이슈명
- 관련 분개 목록
- 거래처별 합계
- 적요 키워드
- 금액 상위 거래
- 법령 근거

출력:

```json
{
  "issue": "업무관련성 의심 복리후생비",
  "summary": "복리후생비 중 병원·가족·개인성 키워드가 포함된 거래가 8건, 합계 4,250,000원 발견되었습니다.",
  "risk_points": [
    "임직원 복리후생인지 대표자 또는 가족 개인비용인지 확인 필요",
    "회사 규정 또는 지급기준 존재 여부 확인 필요"
  ],
  "recommended_action": "증빙과 지급대상자, 회사 복리후생 규정 제출 요청",
  "review_required": true
}
```

### 6-2. 고객 자료요청 문구 생성

입력:

- 부족자료 목록
- 관련 금액
- 법령 근거
- 고객에게 보낼 톤

출력:

```text
업무용승용차 관련비용 검토를 위해 아래 자료를 요청드립니다.

1. 차량별 운행기록부
2. 업무전용자동차보험 가입증명서
3. 차량별 리스·렌트 계약서
4. 차량별 감가상각비 또는 리스료 산정내역

해당 자료가 없는 경우 법인세법상 업무사용비율 및 한도 적용에 따라 손금불산입 금액이 발생할 수 있습니다.
```

### 6-3. 검토메모 초안 생성

입력:

- 조정 항목
- 계산 결과
- 검토 큐
- 법령 조문
- 회계사가 선택한 판단

출력:

```text
검토메모:
당기 지급이자 중 건설 중인 자산 관련 차입금 이자가 포함되어 있는지 확인하였다.
분개 적요상 "공장 신축", "건설", "공사대금" 관련 차입금 이자 거래가 확인되어
건설자금이자 해당 여부를 추가 검토 대상으로 분류하였다.
고객에게 차입금 사용내역과 공사 관련 자금집행 내역을 요청하였다.
최종 손금불산입 여부는 수취 자료 확인 후 확정한다.
```

### 6-4. 선택 거래 정밀 검토

대상:

- 회계사가 직접 선택한 거래
- 금액 상위 거래
- 키워드 위험도가 높은 거래
- 동일 거래처 반복 거래

제한:

```text
기본 10건
최대 50건
초과 시 LLM 실행 전 경고
```

출력은 세무판단 확정이 아니라 다음 형식으로 제한한다.

```json
{
  "transaction_group": "거래처 골프장 접대",
  "possible_issue": "기업업무추진비 또는 업무무관비용 검토",
  "evidence": ["적요에 골프 포함", "거래처가 골프장", "법인카드 증빙 존재"],
  "missing_documents": ["접대 상대방", "업무 관련성 설명", "법인카드 승인내역"],
  "memo_draft": "거래처 접대 목적 여부 및 업무관련성을 확인할 필요가 있다.",
  "final_decision_required": true
}
```

## 7. 화면 설계 변경

기존 4단계 이름:

```text
LLM 정밀 분석
```

권장 이름:

```text
AI 검토 보조
```

### 7-1. 화면 구성

```text
1. 검토 큐 요약
   - High / Medium / Low
   - 항목별 건수·금액
   - 자동계산 가능 / 자료요청 필요 / 수기판단 필요

2. 자료요청 문구 생성
   - 고객 발송용
   - 내부 체크리스트용
   - 항목별 선택 생성

3. 검토메모 초안 생성
   - 접대비
   - 지급이자
   - 업무용승용차
   - 가지급금
   - 부당행위
   - 기부금

4. 선택 거래 정밀 검토
   - 회계사가 선택한 거래만 LLM 실행
   - 기본 10건, 최대 50건

5. 결과 반영
   - 계산에 직접 반영하지 않음
   - 검토메모, 자료요청, 감사추적에 저장
```

## 8. 프롬프트 원칙

### 8-1. 공통 시스템 프롬프트

```text
당신은 대한민국 법인세 세무조정 업무를 보조하는 AI입니다.

역할:
- 세무조정 검토 큐를 요약한다.
- 고객 자료요청 문구를 작성한다.
- 검토메모 초안을 작성한다.
- 회계사가 확인해야 할 판단 포인트를 정리한다.

금지:
- 세무조정 금액을 확정하지 않는다.
- 소득처분을 확정하지 않는다.
- 과세표준·세액을 계산하지 않는다.
- 법령에 없는 규칙을 만들지 않는다.
- 제공되지 않은 사실을 단정하지 않는다.

표현 원칙:
- "확정" 대신 "검토 필요", "확인 필요", "자료 수취 후 판단"을 사용한다.
- 법령 근거가 제공된 경우 그 조문만 인용한다.
- 고객 발송 문구는 정중하고 간결하게 작성한다.
```

### 8-2. 입력 데이터 최소화

LLM에는 원본 전체 분개를 보내지 않는다.

보낼 수 있는 정보:

- 계정명
- 적요
- 거래처명
- 금액
- 날짜
- 증빙유형
- 전표번호
- 원본 행번호
- 관련 법령 조문

보내지 않거나 마스킹할 정보:

- 주민등록번호
- 계좌번호
- 임직원 민감 개인정보
- 불필요한 전체 파일 내용
- 고객 내부 메모 중 세무검토와 무관한 내용

## 9. 감사추적 저장 항목

LLM 결과는 계산 결과가 아니라 검토 보조 산출물로 저장한다.

| 필드 | 설명 |
|---|---|
| 생성유형 | 검토큐요약 / 자료요청 / 검토메모 / 선택거래검토 |
| 관련항목 | 접대비, 지급이자, 차량비 등 |
| 관련전표 | 전표번호 목록 |
| 원본행번호 | 감사추적용 |
| 입력요약 | LLM에 전달한 요약 데이터 |
| 출력본문 | 생성된 메모 또는 요청문 |
| 법령기준일 | 사업연도 종료일 |
| 모델명 | Ollama 모델명 |
| 프롬프트버전 | 프롬프트 해시 |
| 최종반영여부 | 미반영 / 메모반영 / 자료요청반영 / 회계사수정 |
| 수정자 | 회계사 또는 실무자 |
| 수정일시 | 최종 수정 시각 |

## 10. 성능 기준

LLM 실행 시간은 세무조정 업무 흐름을 막으면 안 된다.

### 10-1. 기본 제한

| 항목 | 기준 |
|---|---|
| 기본 선택 거래 수 | 10건 |
| 1회 최대 거래 수 | 50건 |
| 이슈 그룹 요약 | 그룹당 1회 |
| 자료요청 문구 생성 | 항목당 1회 |
| 검토메모 생성 | 항목당 1회 |
| 전체 분개 LLM 분석 | 기본 금지 |

### 10-2. 예상 사용량

| 업무 | LLM 호출 수 |
|---|---:|
| 검토 큐 전체 요약 | 1~3회 |
| 자료요청 문구 | 3~10회 |
| 주요 항목 검토메모 | 5~15회 |
| 선택 거래 정밀 검토 | 10~50건 |

목표:

```text
일반 중소기업 세무조정 1건당 LLM 총 실행시간 5~20분 이내
```

## 11. 검증 기준

LLM의 정확도를 "세무판단 정확도"로 평가하지 않는다.  
LLM은 판단자가 아니라 문서화·요약 보조자이기 때문이다.

평가 기준:

| 지표 | 목표 |
|---|---|
| 자료요청 누락 감소 | 회계사가 추가한 요청 항목 수 감소 |
| 검토메모 수정률 | 사람이 거의 전면 재작성한 비율 감소 |
| 고위험 큐 요약 유용성 | 회계사 평가 5점 척도 |
| 사실 단정 오류 | 0건 목표 |
| 법령 없는 임의 판단 | 0건 목표 |
| 처리시간 | 1건당 실무 흐름 방해 없음 |

## 12. 구현 우선순위

### 1순위: LLM 대량분석 축소

- 고객 발송용 문구 생성
- 내부 체크리스트용 문구 생성

## 12-2. 세무 컨설팅 코멘트 + 참고파일 RAG (2026-06, ADR-006)

"LLM 분개전체분석"을 전면 분석 대신 **세무 컨설팅 코멘트**로 재정의했다. 회사정보·재무제표·세무조정
결과를 바탕으로 자문 토픽을 제시하되, **AI는 판단을 확정하지 않는다**(ADR-002).

- **토픽 발굴 = 규칙엔진(`consulting.py`)** — 결정론적. 토픽은 [현재상황]→[근거(법령+산출논리)]→[결론(시나리오 복수 옵션)]→[참고자료] 4섹션.
  시나리오의 effect 숫자는 규칙엔진 산출값만 인용(신규 금액 생성 금지). 카테고리: 리스크→특례·감면→정책.
- **참고파일 RAG = `src/rag/reference_retriever.py`** — 국세청 PDF/HWP 추출텍스트(`2_참고자료/추출텍스트`)를
  **벡터DB 없이 키워드 검색**. 토픽 키워드로 관련 청크를 retrieve해 근거 자료로 첨부(출처 인용).
  **계산엔진과 분리** — 컨설팅·검토메모·PDF에만 연결. 외부 네트워크/LLM API 없음(로컬 텍스트).
- **LLM 문장화 = `src/llm/consultant.py`(선택)** — 시나리오 action의 **톤만** 다듬는다. effect·요건·숫자·법령은
  프롬프트에서 제외해 LLM이 손대지 못하게 한다(환각 차단). 미가동·실패 시 원문 action 유지(안전 폴백).

law.go.kr 조문 RAG(Level 1, `analyzer.py`)와 참고파일 RAG는 **별개 경로**다.

## 13. 최종 원칙

이 프로젝트에서 LLM은 세무조정 엔진이 아니다.

```text
규칙엔진 = 계산·컨설팅 토픽·숫자·법령 근거
체크리스트 = 누락 방지 + 검토필요 근거법령·해석
참고파일 RAG = 컨설팅 근거 자료 보조 (키워드 검색)
LLM = 설명·요약·자료요청·검토메모·시나리오 문장 톤
회계사 = 최종 판단
```

이 원칙을 벗어나면 로컬 LLM은 느리고 불안정한 병목이 된다.  
반대로 이 원칙을 지키면 LLM은 세무조정 용역의 문서화와 커뮤니케이션 시간을 줄이는 실용적인 보조도구가 된다.
